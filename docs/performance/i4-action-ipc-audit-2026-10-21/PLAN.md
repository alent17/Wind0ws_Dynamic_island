# I4 action IPC source audit — 2026-10-21

## Scope and status

The initial settings audit and its App repair were followed by a read-only transport-boundary design and a default-off four-route frontend aggregate slice. I4 remains unchecked: full transport coverage, disabled-overhead measurement and native acceptance remain open.

## Findings

- **System volume writes now use a serialized latest-value queue.** `src/App.svelte::handleAudioVolume` rounds/clamps to an integer, updates optimistic state, and submits `(deviceId, integer)` to `src/lib/latestValueWriteQueue.ts`. Repeated same-key requests are suppressed; pending values are replaced by the newest one. If a write fails without a newer pending value, dedupe clears so the same value can be retried; if a newer value is already pending, it is sent next instead of being discarded. A→B→A while A is in flight queues the final A rather than letting the earlier A suppress it. Device switching cancels old pending values, ignores slider writes during the switch, and invalidates dedupe after native state is re-read. This is bounded concurrency/coalescing, not a hard frequency cap.
- **The active slider is `VolumePanel`.** `src/lib/components/island/IslandSurface.svelte` renders it and forwards to the App handler. `VolumePanel::endDrag` now submits the actual pointerup coordinate after either click or drag; pointercancel/lost-capture only clean up. `ArcVolumeControl.svelte` remains unused by any render/import call site and is deferred.
- **The COM endpoint is not reused.** `get_system_audio_state` and `set_system_volume` each enter an apartment, create an enumerator, get the default endpoint, and activate `IAudioEndpointVolume`. Calls are dispatched through `commands/native_task.rs`; device switching changes the default endpoint and re-queries state. A shared endpoint cache would need apartment/thread ownership and invalidation on device changes, so it is a higher-risk follow-up, not part of the first slice.
- **Floating window creation is now single-flight.** `open_floating_window` uses a static Tokio mutex and a small `find_or_create_window` seam around lookup/build; the guard remains alive through existing show/focus/animation work so concurrent opens serialize. This is an async lock, never a `std::sync::Mutex` held across await. Build errors propagate, and guard drop permits retry. Timer and Studio use the same Tokio-lock pattern. Known frontend open callers are App and Studio, both using this command; close remains outside the gate and retains existing token events.
- **Settings save/update emits one full snapshot plus changed-field events.** Rust `AppPreferences` has `#[serde(rename_all = "camelCase")]`; `commit_settings` serializes commits with `settings_writer`, returns early for no-op values, applies/persists once, updates state and a backend revision, then emits `emit_setting_diffs`, one full `settings-updated`, and one `settings-committed` marker. `update_settings` receives a JSON patch whose keys are camelCase. The full snapshot is a camelCase `AppPreferences` object. `settingsStore` types it as `Partial<AppSettings>` for compatibility, merges through each WebView's normalizer, increments a local arrival revision, and only publishes when JSON changes; that revision protects the initial `get_settings` response from overwriting an event, but it is not a backend revision.

  App's store listener and its second `settings-updated` handler are separate subscriptions, not duplicate store writes: the latter syncs capture visibility, while `$appSettings` drives one reactive placement effect. For App's monitor picker, `switchMonitor` already moves to the selected monitor before saving; the later full-store placement effect is protected by `lastPlacementInput`/`lastAppliedBounds` dedupe. Thus no repeated bounds animation was found in that chain. Floating's full-event callback and field listeners also have distinct roles: the MV full callback only assigns the flag, while the field event owns the resolver/playback side effect; the HD/lock/pixel/halftone/topmost fields are not otherwise handled by its full callback. No duplicate HD resolver, spectrum-device refresh, or Rust topmost write is demonstrated by one save.

  Studio's initialization is a small duplicate DOM-side effect: after `connectSettingsStore`, it calls `applyExternalSettings(connection.settings)`, subscribes (Svelte invokes the subscriber immediately with the same store value), then calls `applyAppFont` and `setLocale` again. `applyExternalSettings` itself sets font and locale, so initial setup writes the font custom property / document language three times. This path performs no native IPC; `setLocale` also sets the same locale store value. It is lower priority than the App `get_settings` invoke.

  `always-on-top-changed` and `corner-radius-changed` have no current frontend consumers, but their public events may be compatibility surfaces; do not delete them in this audit. Avoid introducing another settings revision protocol.
- **Spectrum bypasses EventBus statistics.** The native publisher emits `spectrum-data` directly from `src-tauri/src/audio.rs`; `spectrumStore` listens to that name. The EventBus helper and frontend `AUDIO_SPECTRUM` constant use `audio-spectrum`, and no call sites bridge the two. Existing EventBus counters therefore do not describe the live spectrum path. Treat complete invoke/emit/receive/byte instrumentation as a separate design task; define consistent event identity and default-off sampling before implementation.

## Recommended first slice

Implemented the volume correctness/coalescing slice in `src/App.svelte`, `src/lib/latestValueWriteQueue.ts`, and `src/lib/components/volume/VolumePanel.svelte`:

1. At the App boundary, skip a write when the clamped integer equals the value already represented by the latest optimistic/pending state, without dropping a return-to-in-flight value when a different latest value is queued.
2. On successful `pointerup`, compute and submit the terminal value from the final pointer coordinate for both click and drag; keep cancel/lost-capture from submitting a terminal value.
3. Preserve the existing one-in-flight/latest-pending queue. Do not claim a hard command-rate cap in this slice; if measurements still show excessive calls, add an explicit maximum dispatch rate in a separate step with guaranteed final-value flush.

Focused verification passed: 5 deferred queue unit tests cover duplicate key, pending replacement, A→B→A, failure retry, owner cleanup, same-device external invalidation, and device-key changes; 2 Playwright component tests cover pointerup without a final move, no delayed extra write, and pointercancel. `pnpm check` reports 0 errors/warnings and the production frontend build completed (3,871 modules). A one-minute real drag should still confirm final OS volume and command counts follow integer transitions. Native Windows volume/device-switch behavior is not yet accepted.

## Settings snake-case repair (implemented)

In App's `SETTINGS_CHANGED` consumer, the exact built-in `monitor_index` marker now skips only the redundant refresh, relying on the full snapshot emitted immediately afterward by `commit_settings`. The existing camelCase `monitorIndex` path and unknown-name refresh fallback remain. Unknown fallback publication uses the existing `refreshSettingsStore` guard to avoid publishing after App disposal. No field-specific event or settings store architecture changed. This does not promise behavior for third-party emitters that send snake-case without a full snapshot.

Two App Playwright fixture tests passed: one emits `monitor_index` → full `settings-updated` → `settings-committed` and verifies no extra `get_settings`, monitorIndex 1 in the store, and exactly one necessary placement; the other verifies the camelCase command path, unknown fallback refresh, suppression of a delayed fallback result after disposal, and no listener effects for events emitted after disposal. `pnpm check` reports 0 errors/warnings and `pnpm run build` completed (3,871 modules). Studio's duplicate initialization font/lang DOM writes remain low priority and unchanged.

## Minimal transport diagnostics design and first implementation

This is a bounded, opt-in aggregate for the optimized paths in this audit; it is not a general Tauri IPC trace. The first frontend-only slice is implemented below; its coverage is intentionally narrower than the complete design.

### Implemented first slice

`src/lib/transportDiagnostics.ts` owns a fixed four-route schema (`mediaSync`, `timerState`, `region`, `volume`) with default-off module state and explicit session-only `enable`, `disable`, `reset`, and `snapshot` functions. Only the lifecycle test fixture imports the control/readout functions. There is no product UI, persisted setting, global console/window diagnostics API, cross-window diagnostic event, automatic enable, bytes counter, or diagnostics timer. Snapshots identify their scope as `this-webview`; counts from separate WebViews must not be summed as though this were a global trace. No payload, title, artwork, device key, session token, or other identifiers are retained.

Instrumentation follows one owner per measurement: `mediaSyncSender` counts queue offers/replacements/retries and dispatch outcomes; App's readiness gate counts offers blocked for no active consumer; Floating's designated event listener counts receives. App's `dispatchTimerSnapshot` counts actual state/request dispatches and outcomes; TimerWindow's listener counts receives. `islandRegionSender` counts queue offers/replacements/dedupe/retries, while App wraps only the native command dispatch for attempt/outcome and duration. `LatestValueWriteQueue` counts volume dedupe/replacement, while App wraps only the actual `set_system_volume` dispatch for attempt/outcome and duration. This avoids counting queue sends a second time at a generic IPC layer. Timer `received` is read in the TimerWindow's WebView and is therefore a separate scoped snapshot in a real app run.

The disabled checks return before `performance.now`, counter work, action wrappers, byte work, or timers. Event/command action closures used only for diagnostic tracking are constructed only in the enabled branch. No extra serialization or payload inspection was added. The existing region signature serialization remains part of queue behavior and is not a diagnostic byte measurement. Exact serialized bytes, estimated bytes, Spectrum, Rust EventBus/direct emits, native window events, other invokes/listeners and Tauri internals are not measured by this slice.

Focused verification: `transportDiagnostics.test.ts` checks default-off/no clock/no timers, allowlist/counters/duration/reset, and late completion across enable generations; queue/media sender unit targets passed. Three lifecycle Playwright cases passed for no-ready-consumer media sends and ready receives, one in-flight region command, change-only Timer snapshots while running, and the VolumePanel fixture's latest-value queue dedupe with one mocked `set_system_volume` dispatch. `pnpm check` reports 0 errors/warnings and `pnpm run build` transformed 3,872 modules. These are structural/counter behavior checks only: disabled-path overhead was not benchmarked, no IPC byte/total reduction is claimed, and Spectrum/full transport remain uncovered.

### Minimum useful first slice

Use allowlisted route IDs and aggregate counters only. A route has one producer owner; a consumer count is recorded only at the intended listener. Do not sum EventBus counts with endpoint counts for the same hop.

| Route | Producer counters | Consumer / result counters |
|---|---|---|
| App → Floating media sync | At `createMediaSyncSender` dispatch: dispatch attempts, success/failure, retries, offers replaced while pending. At App's readiness gate: offers blocked because no ready consumer, counted once at that gate. | At Floating's `ISLAND_MEDIA_SYNC` listener: payloads received and revisions accepted/stale-dropped. `emit` success remains separate from receive. |
| Timer state snapshot | At `dispatchTimerSnapshot`: sends, forced request replies, duplicate revisions skipped, failures; this event is state-on-change/explicit request, so it can verify that there is no per-second broadcast. | At TimerWindow's `TIMER_STATE_CHANGED` listener: snapshots received and revisions accepted/ignored. Timer's local second-boundary display ticks are not IPC events and need no diagnostic timer. |
| Interaction region | At `createIslandRegionSender`: offers, pending replacement/coalescing, acknowledged-signature no-op, actual sends, retries and failures. Do not additionally count the same command in a generic invoke total. | The native command completion is the result boundary; count successful/failed completions and elapsed time there, but do not invent a frontend receive counter for a command with no event listener. |
| System volume | At `LatestValueWriteQueue.submit`/write callback: same-key dedupe, pending replacement, actual `set_system_volume` dispatches, failures, and completion latency. Keep device identifier and value out of exported aggregates. | Command completion success/failure is the result; there is no event consumer. |

For spectrum, add an optional separate hot-path aggregate at the direct `spectrum-data` publisher and `spectrumStore` listener, since EventBus does not see it. Count published frames, sampled/accepted frames and last/max inter-arrival gap using local thread-owned counters; flush aggregate snapshots at a coarse interval only while enabled. Never serialize each frame, acquire a shared diagnostics mutex per frame, or emit a diagnostics event per frame. A safe raw-size reference is `size_of::<[f32; NUM_BARS]>()` (24 bytes for six `f32` values); label it **raw payload bytes**, not wire bytes. If estimating JSON representation, use a documented sample and mark it `estimated`, with sample count and method. No payload values, track metadata, artwork, settings, process names, or device identifiers are retained.

### Byte and latency semantics

- Call a byte count **exact serialized bytes** only when measured from the serialization already used to send that payload. No current central hook exposes such bytes. Do not serialize an additional copy just to measure it.
- For low-frequency fixed-shape payloads, optional sampled size estimation may be calculated only after diagnostics is enabled; label it **estimated JSON payload bytes**, include the sampling rate/count, and do not include Tauri framing or claim wire size. Skip content-derived sizes for `settings-updated` and other private or variable-content payloads; count the event only.
- For invoke/command latency, measure one monotonic start/end around the selected dispatch and completion. Store count plus bounded histogram or sum/max buckets to derive useful percentiles; no per-call logs. These are end-to-end call-site durations, not a decomposition of Tauri, scheduling, or native work.

### Switch, readout, and disabled behavior

Provide a session-only, default-off switch and aggregate snapshot/reset/export API, reachable only through an explicit diagnostics action. Do not persist it in user settings, registry, or startup configuration. The disabled branch must be a single cheap flag check at each selected boundary: no clocks/timers, payload inspection/serialization, allocation, mutex acquisition, or cross-window diagnostics event. Enabling diagnostics may start one coarse snapshot-flush timer; disabling it and app shutdown must stop that timer, clear pending flush work, and release/reset in-memory aggregates. Export returns only the allowlisted aggregate schema, without raw payloads or identifiers.

Before implementation, define a disabled-path review/verification that checks the flag guard occurs before timing, byte estimation, allocation, lock acquisition and timer setup at every instrumentation point. Any performance comparison should then measure that disabled path against an uninstrumented build; this design pass does not run tests/build or claim an overhead result.

Existing `c2-media-probe` is a bounded, windowless harness for the production SMTC listener/EventBus path. It may later host a focused EventBus aggregate exercise, but it does not observe frontend receives, direct spectrum publishing, invoke calls, window events, or Tauri internal IPC and is not a transport-wide probe. No new test platform is proposed.

### Coverage limits and review gate

The first implementation should cover only the four optimized routes above, plus separately gated spectrum aggregates if required. Do not add a generic invoke wrapper and label it “all IPC”; it cannot see Rust direct emits, all listener callbacks, or Tauri internals. Do not count the same producer send at both EventBus/API wrapper and route queue. A later full trace would require instrumentation below the current app API, which is outside I4's minimum diagnostics scope. I4 stays unchecked until the design is reviewed, the opt-in implementation is measured with diagnostics disabled/enabled, and native route behavior is accepted.

No real Tauri window or click acceptance was performed; I4 remains unchecked.
