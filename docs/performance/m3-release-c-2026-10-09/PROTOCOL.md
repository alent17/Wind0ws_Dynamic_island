# M3 Release Benchmark C 对照协议

当前验收正在进行，M3 保持 `[ ]`。本记录不把之前的 debug/GPU 波动归因为泄漏或收益；此前 GPU 回稳仍标为“未证实”。最终结论以本目录的结果报告为准。

## 配对构建

两侧从 `0055ebe` 提取已提交源码，保留相同 M2 修复。优化前侧撤回 `74db42b` 的 M3 预算实现，使用 `2340164` 的对应原生服务以及旧的 Canvas 分配/缓存规则；不撤回 M2 的同曲目接收、初始快照版本保护或 Canvas DOM owner。

Cargo.toml、Cargo.lock、release 编译参数、M2 共用模块、原生和前端测量适配器保持一致。`tokio sync` 依赖能力两侧都保留，优化前不会因此启用 M3 的并发预算。源码差异由哈希清单限定为 M3 文件集合。Release 使用 `opt-level=s`、LTO、单 codegen unit、`panic=abort` 和生产前端构建；二进制哈希另存构建清单。

工具仅向隔离源码副本注入适配器，未改工作目录的业务源文件。复现入口为 `scripts/benchmark-c/prepare-sources.py`，再为各源码目录建立指向现有 node_modules 的 junction、运行生产前端构建及原生 Release 构建。

## 固定条件

- 同一组 100 个歌曲 ID，固定顺序；额外一首固定预热曲目不计入 100 首。旧 M2 记录未保存 ID，同名/同歌手版本在当前队列中按稳定第一项选定，新的对照从此以 ID 为准。
- 浮窗 200×395，DPI=1，HD 开启、像素化关闭、MV 关闭。其余设置使用同一份快照；每次绘制检查 DPI 与窗口尺寸。
- 实时 Spectrum 保持共享设置中的开启状态；恢复阶段是暂停播放器并保持现有窗口/设置，不等同于关闭所有功能的 B0 Idle。发布的设置清单隐藏了与本测试无关的天气位置；构建清单中的设置 SHA-256 对应本地未经脱敏的实际共用快照。
- 播放器队列先完整预热，原始队列与模式在本地备份。准备阶段通过本地播放器控制接口设置 101 项队列、重新编号排序索引并确认顺序；正式阶段断开 CDP，仅用 Windows SMTC 控制。
- 每轮使用全新的可执行目录、Isle 媒体缓存和 WebView 数据目录。以相同额外曲目预热 60 秒后开始采样，连续切换 100 首，每首至少停留 5 秒并等待绘制/HD 解析完成。
- 六轮顺序：前1、后1、后2、前2、前3、后3。浮窗始终打开，正式轮结束后暂停播放、保持窗口打开观察 300 秒恢复。

## 素材与旁路回放

预跑发现在线封面失败与原队列排序索引会影响可比性，预跑数据全部标为非正式。正式数据使用一次性下载、验证并冻结的真实 1200 像素封面素材，按固定 64 KiB/16 ms 分块进行本地 HTTP 回放；实际经过两侧各自的下载、解码、输出、磁盘缓存与 Canvas 路径。时长查询所附带的封面下载也使用同一元数据/素材回放。它们的业务调用及重复工作没有被取消。

《Body》的提供方及刷新后的封面链接均返回 404，保留该曲目真实 SMTC 缩略图（108×108）并单独标注 HD 不可用，不补造封面或替换歌曲。源文件 SHA-256、尺寸、字节数、来源和完整 ID 列表保存于本地清单。各轮读取的传输输入另记录长度和一致性哈希；六轮输入不一致会阻止对照通过。

本次测量隔离外部搜索/CDN抖动，用于资源预算对照，不外推在线搜索服务的实际耗时。普通使用路径的在线服务可靠性不在本次性能结论内。

回放 URL 按索引固定为 101 个键（含预热），原提供方 URL 共 98 个不同值、文件 SHA-256 共 94 个不同值。两侧使用完全相同的键集合，但该设计不保留原服务少数跨歌曲复用 URL 的缓存命中，因此绝对值属于本回放场景，不能直接当作普通在线播放的内存预测。

首次使用 `127.0.0.1` 的组被作废：优化前缓存的既有内部地址检查拒绝该地址，随后走 Base64 回退，优化侧却写入缓存，不能比较预算收益。正式组改用两侧均接受的同一 loopback 地址 `127.0.0.2`；预跑确认两侧采用缓存路径，原始旧组保留在 `runs/` 并记录无效原因。

之后的 `runs-final/` 在主机于 2026-10-09 08:05:57 重启时中断（优化后第 1 轮停在 49 首）。该组整体排除，避免混用重启前后的系统状态。重启后重新启动播放器、完整预热固定队列，再从第 1 轮开始；最终六轮仅取全新 `runs-session2/`，不拼接中断数据。

## 指标口径

正式轮不打开 Isle 调试端口、DevTools、HeapProfiler 或强制 GC。相同的轻量适配器仅在绘制/下载完成及场景标记时写记录；OS 采样器记录指定 Isle 后代进程树的 CPU、Private Commit、Renderer 内存及 per-PID GPU committed memory。

- 进程树峰值为采样最大值；单进程 pagefile 高水位单列，不能相加当作同一时刻的进程树峰值。
- 下载峰值为已跟踪的响应/传输分块缓冲；解码峰值为已跟踪的 DynamicImage 像素缓冲。这些计数不含内部 decoder scratch、HTTP 内部缓冲或 WebView 解码分配，须结合原生/Renderer/进程树内存判断。
- 延迟起点为 SMTC 控制请求时间，终点为原生收到 Canvas 绘制完成记录，另保存驱动总耗时；它不是 compositor 实际呈现时刻。
- GPU 恢复以完整曲线和重复轮次判断；单个端点不能证明回稳、泄漏或收益。

复核发现优化前的文件探针位于写缓存之后，可能与同 key 的另一个写入竞争。六轮完整观测的 101 份输入长度/哈希一致，但优化前三轮另有 4/6/5 次短读，优化后为 0；短读原样列入汇总，不拿它们充当传输输入身份。全部 100 首的末次绘制图片尺寸均匹配固定语料。该限制与最终显示诊断共同报告，不能从文件短读次数直接推出错图次数。

堆快照、像素正确性、实际显示源图片质量、Canvas 实际显示截图与每 25 首关闭重开，另跑 CDP 诊断/回归轮，不混入正式性能轮。图片源像素对照与 Canvas 显示截图对照分别列出，避免只比原始图片、遗漏 backing 缩小后的显示差异。连续场景检查 renderer PID 集合保持不变；关闭重开场景单列，避免销毁进程掩盖累积趋势。

本地缓存 asset 图片会 taint Canvas，直接 `getImageData` 的预跑因此失败。诊断没有禁用跨源安全检查，改用 CSS 尺寸截图与相同源字节、相同 backing 尺寸的浏览器参考图对照。记录内部区域 MSE，采用 RMS≤8 RGB levels 或三点≤2 的判定，容纳 compositor 缩放采样差异。临时参考 Canvas 在每次检查后删除，堆快照在之后单独采集；该相似性判定不宣称逐像素完全相同。前面的 taint/采样方法预跑保留于单独目录，不加入四个正式诊断结果。

首组显示截图曾包含悬停按钮与遮罩，它们不能当成图像预算造成的画质差异。两侧完整重跑固定指针离开视口的 100 首连续质量诊断，最终画质/连续诊断使用 `diagnostic-hover-fixed/`，重开回归使用原 `diagnostic/{before,after}-reopen/`；旧画质对照保留为 `quality-comparison-hover-uncontrolled.json`，不参与最终质量结论。
