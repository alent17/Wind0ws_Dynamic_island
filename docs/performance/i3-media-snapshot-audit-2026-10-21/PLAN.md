# I3 media snapshot/source audit

This note records the initial read-only audit and thirteen implementation slices in the m3-release-c worktree. I3 remains unchecked because cross-channel ordering, delivery latency, native behavior and performance acceptance remain open.

## Data path and payload contract

1. **Rust actor and snapshot.** `src-tauri/src/lib.rs::spawn_media_listener` owns one GSMTC manager, manager/session event subscriptions, a capacity-one refresh-message queue, and a `MediaListenerMetadataCache`. SMTC callbacks invalidate metadata and enqueue a refresh marker; a bounded 1/2/5-second poll remains as fallback. `services/media.rs::get_media_info_from_manager_for_listener` keeps metadata for a concrete session and reuses it until invalidated/TTL refresh. This is C2 work already in place and should be kept.
2. **Rust event.** The actor builds a complete `MediaState` snapshot on each successful refresh. It omits only `albumArt` when the same source/title/artist still has identical artwork; an empty `albumArt: ""` is retained for a clear. Empty-session state is emitted only after two confirmed misses. `EVENT_BUS.emit_media_update` still applies a 500 ms leading throttle; within the interval it increments `total_dropped` and returns legacy `Ok(())` without a trailing send. The fourth slice adds a media-specific observable outcome and commits `last_artwork_track`/`last_artwork` only when `app.emit` succeeds, so the next actor snapshot retries a dropped full-cover update. Confirmed-empty publication likewise stays pending until emitted. `control_media(play_pause)` separately reads a snapshot and calls unthrottled `EVENT_BUS.emit`, creating a second publication route.
3. **Main App.** `App.svelte` listens through `onMediaUpdate`, which registers directly with `eventManager.on` and no longer applies the frontend 500 ms leading-drop throttle. It maps raw snapshots into island-local playback/artwork state, then calls `syncFloatingMediaClock`. The function projects position, stamps local `Date.now()`, and offers a full local snapshot to the single-flight `mediaSyncSender`; the Floating listener receives this derived `island-media-sync` and raw `media-update`. The sender retains at most one latest full pending snapshot while an emit is in flight, compares artwork to the last Tauri-accepted baseline only at dispatch, and omits `albumArt` only when that acknowledged track/art is unchanged. Failure does not advance the baseline and receives finite backoff retries; a later sync replaces pending state and retries immediately. After App media listeners are installed it emits `floating-media-ready-query`; a ready token resets the sender's consumer generation. App only replays after the current App mount has received a real native media event. The twelfth slice now gates offers on both a current ready instance token and native media readiness, and clears the queue/baseline when that consumer pauses/closes. Tauri emit success is not proof a listener consumed the event.
4. **Floating window.** `FloatingWindow.svelte` subscribes to `island-media-sync`, raw `media-update`, and `floating-media-ready-query`, then requests `get_media_info_cmd` as an initial full snapshot. After both media listeners are installed and that snapshot succeeds or fails, it emits `floating-media-ready` with a per-instance `crypto.randomUUID()` token; later ready queries re-announce that same token. Its `mediaEventRevision`/`artworkRevision` token protects the initial snapshot from some later events. For 2.5 seconds after an authoritative sync it still suppresses raw playback fields while reconciling artwork. It has no shared sequence comparison for subsequent events from the two authorities. The event timestamp is used for position projection, not ordered against earlier arrivals.
5. **Studio.** `mediaStore` is module-local to each WebView; it is used by Studio, not shared with App or Floating. The initial audit found Studio issuing its own snapshot before `connectMedia` and the store starting refresh before listener registration; the second slice below removes both races and the duplicate query.

Payload meaning today:

| Field shape | Meaning/consumer behavior |
|---|---|
| Most `MediaState` properties present | Full snapshot for metadata, playback, capabilities and timing. No explicit `full`/`delta` marker exists. |
| `albumArt` absent | Delta omission: preserve current same-track art. Rust emits this only for unchanged art; App uses `withoutArtwork` for same-track floating clock updates. |
| `albumArt: ""` or `null` | Explicit clear in `artworkValue`; Rust's `String` serializer produces empty string, not null. `null` is supported by frontend aliases but not emitted by the Rust model. |
| `shuffleActive` / `repeatMode` unavailable | Rust `Option` serializes as JSON `null`; the TS interface marks these fields optional but not nullable. Consumers may receive runtime null despite the TS type. |

`lastUpdatedTimestamp` is not a revision. Rust stamps snapshots with wall-clock milliseconds; App replaces it with local receive/sync time; Floating and `mediaStore` do not use it to reject old events. There is no source sequence shared by actor events, command snapshots and App-generated sync events.

## Existing C2 behavior and tests

- Keep the actor-owned manager/session subscriptions, capacity-one refresh marker, metadata cache, event invalidation counter, bounded fallback polling, confirmed-empty handling and large-art omission. These address native query/cache cost; they do not provide one shared latest snapshot for commands and windows.
- `mediaStore.publish` already distinguishes omitted artwork from empty/null clear and clears art on track change. Its `updateVersion` prevents a snapshot started before an installed event from replacing the event; `artworkVersion` lets a same-track snapshot fill an artwork omission but not revive an explicit clear.
- Both current main App and Floating same-track paths already consume a changed `albumArt`; the I3 plan's older “same-song branch ignores albumArt” statement is not true for the inspected current code.
- Existing tests: `src-tauri/src/lib.rs::media_delta_tests` covers artwork omission versus empty clear, polling intervals and refresh invalidation when the queue is full. `src/lib/mediaStore.test.ts` covers shared listener lifecycle, late listener cleanup, event-before-snapshot, reconnect generations, omitted/cleared artwork and delayed-cover preservation. `src/lib/mediaArtwork.test.ts` covers alias/null/empty artwork and snapshot decisions. `src/utils/eventManager.test.ts` now covers closely spaced media events, independent consumers, exception isolation, disposal, and preserved throttling for other low-priority events. There are still no tests for the App-to-Floating duplicate path.

## Confirmed gaps and evidence limits

1. **Rust leading-drop throttle remains; baseline retry fixed in the fourth slice below.** The media-specific EventBus API now reports throttled, disabled, emitted, or an error separately. The actor retries a changed cover/confirmed-empty snapshot on its next existing poll when the result was not emitted. The throttle still does not retain an immediate trailing send, so latest-state convergence can wait for the existing 1/2/5-second actor cadence. Frontend `onMediaUpdate` no longer independently drops events; this still does not establish end-to-end delivery to every WebView. Event frequency and user-visible impact were not measured.
2. **Floating duplicate authority.** A floating WebView consumes raw Rust snapshots and derived App snapshots for the same fields. The raw listener is throttled; the sync listener is not sequence-tagged. `lastIslandMediaSyncAt` skips some recent raw playback updates but still separately reconciles artwork. Out-of-order delivery can therefore choose state by arrival path rather than source freshness. This is a credible race from independent event channels; no runtime trace proves it happened.
3. **Same-track initial snapshot could revert playback state (fixed in the first I3 slice below).** Before the slice, `snapshotDecision` returned `"accept"` when the event counter advanced but the track key was unchanged and artwork revision was unchanged. `FloatingWindow.handleMediaUpdate` then applied the initial command snapshot's playback/timeline fields after a newer same-track pause/seek event. Native snapshot latency frequency remains unmeasured.
4. **Studio listener-registration race (fixed in the second I3 slice below).** Before the slice, `mediaStore.connectMedia` started refresh before `listen("media-update", ...)` completed, and `Studio.enableLivePreview` issued a duplicate command snapshot. A late listener or snapshot could outlive the final consumer.
5. **Consumer-ready handshake and gate.** The sixth slice installs a Floating-ready token after listener registration and initial snapshot handling; App also queries for an already-ready Floating instance after App listener setup. The twelfth slice gates media sends on this token and App native-media readiness, then pauses the sender on hidden/closed/unmounted notifications. Emit resolution still does not prove a Floating listener consumed the replay; no runtime loss frequency is measured. A stale `FLOATING_MEDIA_NOT_READY` from a prior App session is now ignored when it carries a mismatched session ID; legacy untagged notifications remain accepted.
6. **Timer bridge is separate.** The thirteenth slice changed App fan-out to state-revision changes plus explicit request replies, added App session/revision fences and absolute `endsAt`, and made the Timer window request a fresh snapshot after listener registration and on visibility recovery. Timer display-second updates remain local; there is no per-second App broadcast. Native multi-window delivery and acceptance timing remain unmeasured.

## First safe implementation slice

Fix only **FloatingWindow's initial snapshot reconciliation** using the existing `mediaArtwork.ts` decision helper. When any same-track event arrives after the snapshot token, do not apply the snapshot's playback, position, duration, capabilities or timestamps. If the current track still matches and no explicit artwork update/clear occurred since the token, allow only the snapshot's full `albumArt` to fill a prior omission. If track or artwork changed, discard the stale cover as well. Keep the current Rust actor/cache, event routes, polling, throttles and click/UI behavior unchanged in this slice.

Add deferred tests at the decision/adapter actually used by `FloatingWindow`:

- Start an initial snapshot, deliver a same-track pause/seek event, resolve the old snapshot; play state and position must remain from the event.
- Start a snapshot, deliver a same-track delta with `albumArt` absent, resolve a full snapshot; only its cover may merge, while event timing/playback fields remain untouched.
- Deliver explicit `albumArt: ""` and `albumArt: null` clear while the snapshot is pending; the old snapshot must not revive art.
- Switch tracks while a snapshot is pending; reject the old snapshot entirely.
- Deliver two same-track updates out of order in a pure adapter test; state ordering must use the captured local event revision and must not claim a backend sequence that the payload does not carry.

## First-slice implementation and verification

- `FloatingWindow.svelte` now rejects an initial command snapshot after any newer event for playback, timing, capabilities and metadata. When the player was initially empty and exactly one track arrives during the request, a same-track snapshot may fill only a missing cover; existing or explicitly cleared art is left alone.
- `mediaArtwork.ts::snapshotDecision` now returns `accept`, `artwork-only` or `discard`. The snapshot token includes a local track generation and starting track key. A generation change rejects A→B→A even if the final key matches; the single initial empty→track transition is allowed for the cover-only case. This is a consumer-local revision, not a backend sequence.
- Deferred Playwright coverage exercises the real FloatingWindow listener and pending command snapshot: pause/position/duration/capabilities preservation with a cover fill, empty-string and null clears, A→B→A rejection, and resolving the request after unmount. `mediaArtwork.test.ts` and `mediaStore.test.ts` both pass (10 tests total); the five focused FloatingWindow lifecycle cases pass. `svelte-check` reports 0 errors/warnings and the Vite production build succeeds.
- The first slice leaves separate raw `media-update` and derived `island-media-sync` authorities, leading-drop throttles, App-to-Floating open-window gating, and timer fan-out for later work. The third slice below removes the frontend `onMediaUpdate` leading drop but leaves Rust delivery unchanged. I3 remains unchecked.

## Second-slice implementation and verification

- `mediaStore.connectMedia` now returns its idempotent release function immediately. The first consumer starts one shared setup; additional consumers share it. `media-update` registration completes before the single initial command snapshot begins. If listener registration fails, the store still requests a first snapshot and starts its existing 2.5-second polling fallback.
- Releasing a consumer removes its readiness callback immediately. Releasing the last consumer increments the connection generation, disposes an installed listener, and clears polling. A listener that resolves after release/reconnect is disposed without triggering a snapshot; a stale snapshot cannot publish into a new generation.
- Snapshot refresh captures update, artwork and local track generations. A same-track event during the request wins for media fields and may receive a missing cover only when there was no explicit artwork change/clear or track transition. A→B→A in one connection invalidates the old cover. The demo placeholder is not considered the native track baseline.
- Studio no longer calls `getMediaInfo` directly. It uses the store snapshot once and switches from its demo preview to live mode only after an event or successful snapshot marks the connection ready. If native reads fail, the deterministic demo preview remains visible while the 2.5-second fallback continues.
- Added deferred tests for listener-before-snapshot ordering, event-before-snapshot completion, shared initialization, immediate release and late-listener disposal (including reconnect), listener failure plus 2.5-second polling, reconnect generation, explicit art clear and A→B→A stale-cover rejection. Studio Playwright coverage verifies one initial `get_media_info_cmd` and that the demo preview remains until live state arrives. `mediaStore.test.ts` + `mediaArtwork.test.ts` pass (14 tests); five FloatingWindow lifecycle tests and one Studio initialization test pass (6 total); `svelte-check` reports 0 errors/warnings and the Vite production build succeeds.
- Remaining I3 work: separate the raw and derived media authorities; Rust-side leading-drop delivery; App-to-Floating open-window gating/baseline acknowledgement; and timer fan-out. I3 remains unchecked.

## Fourth-slice implementation and verification

- `EventBus` now exposes `EmitOutcome::{Emitted, Throttled, Disabled}` through a new outcome-returning API while preserving existing `emit`/`emit_with_options` and `emit_media_update` unit-result interfaces. An uninitialized AppHandle or Tauri send failure remains an `Err`; only a successful `app.emit` returns `Emitted`. The emitter test seam covers all four cases and checks stats only acknowledge an actual successful call.
- The media actor computes a candidate artwork baseline but does not commit it before serialization/emission. `MediaEmitBaseline` commits artwork replacement/clear only for `Emitted`; `Throttled`, `Disabled`, serialization failure and send error retain the prior baseline so the next existing actor refresh rebuilds a full current snapshot. Same-track omission is still allowed after an emitted baseline has been acknowledged.
- `empty_state_emitted` and artwork-baseline clearing now advance only after an emitted confirmed-empty event. A confirmed empty event that is throttled/disabled/errors is retried at the existing five-second empty poll cadence (no new timer/queue); after success it is not repeated until a session returns. The C2 probe counts `empty_emit_success` only for `Emitted` and reports throttled/disabled separately; error/payload-error counters remain separate.
- Pure transaction tests cover emitted/throttled/error outcomes, artwork replacement and explicit clear acknowledgement, same-track omit after acknowledgement, and confirmed-empty retry/stop behavior. `cargo test --locked --offline --lib -- --test-threads=1` passes 100 tests with one existing Windows-audio-service test ignored; `cargo check --locked --offline --lib` and `cargo check --locked --offline --features c2-media-probe --example c2-media-probe` pass. The default parallel lib run initially hit two unrelated existing test failures; the complete single-thread run passed.
- The Rust 500 ms leading-drop interval remains. This change prevents the actor from treating a dropped emission as an artwork/empty-state acknowledgement; it relies on the actor's existing poll to retry and does not provide immediate trailing delivery or prove that every registered frontend listener consumed the event. `control_media`'s direct publication path and actor subscription/cache/poll strategy are unchanged.

## App-Floating authority audit and consumer-ready implementation

### App-to-Floating sync triggers and consumers

`App.svelte::syncFloatingMediaClock` is called from these paths (observed at source, not inferred from an event trace):

- Main-island recovery: `recoverMissingMetadata` emits after a metadata lookup and again after the recovery attempt; a recovered NetEase album image emits after image load (`App.svelte:101-140`).
- Floating-window open: after `openFloatingWindow()` resolves, App sets `isFloatingWindowOpen = true` and emits one sync (`App.svelte:960-970`). That boolean means the open command completed; it does not prove the Floating WebView mounted or installed listeners.
- Seek: optimistic position is emitted before `seekMedia`; a rejected request rolls back and emits again, guarded against a track change (`App.svelte:1064-1081`). Floating progress therefore currently depends on `island-media-sync` to show this pending seek before a native snapshot confirms it.
- Native media update: each consumed raw media event updates App-local state and emits, including session clear (`App.svelte:1450-1624`).
- Artwork enrichment: the App resolver emits after loading a higher-resolution image and marks `artworkResolved`; recovery can supply richer cover/duration metadata too (`App.svelte:101-140,1587-1618`). Floating uses `artworkResolved` to cancel its own cover lookup and accept this image (`FloatingWindow.svelte:758-775`). Deleting App sync without a replacement would remove current enrichment and optimistic-seek behavior.

The function projects the App island's position, writes local `Date.now()` to `lastUpdatedTimestamp`, and offers a full `MediaState`-shaped payload. Dispatch omits `albumArt` only if the acknowledged track/art matches. The in-flight queue, failure handling and retry behavior are described in the fifth-slice implementation section below. Emit resolution only acknowledges the Tauri emit call; it does not acknowledge that a particular Floating listener consumed the payload.

`isFloatingWindowOpen` is set after the open command returns and cleared on `FLOATING_WINDOW_CLOSED`; the close event is emitted by the native close command after the window closes (`App.svelte:1450-1458`, `commands/window.rs:1540-1543`). The sixth slice adds a ready token after Floating installs sync/raw listeners and completes or fails its first full `get_media_info_cmd` snapshot. App also emits a ready query only after registering its ready receiver and native media listener, so an existing Floating instance can re-announce its token after App reload. On first creation the native window is still built hidden, shown and animated by `commands/window.rs::open_floating_window`; the handshake adds no native lifecycle changes. The initial command snapshot recovers native fields, while the subsequent full App replay restores App-only pending seek and richer cover state.

### Current raw-vs-derived arbitration

The Floating listener subscribes to `island-media-sync` first, raw `media-update` second, then starts the full command snapshot; it installs the ready-query listener before requesting that snapshot and announces ready only after snapshot handling settles (`FloatingWindow.svelte:917-945`). After an authoritative sync it records local receipt time; for **2,500 ms** (not 1,000 ms), raw native playback fields are ignored. Same-track raw artwork is still reconciled during that interval (`FloatingWindow.svelte:796-803`). Outside it, both sources can update playback state; there is no common source sequence. The timestamp affects position projection but is not an ordering token. A delayed raw event after the timeout or an older sync that arrives later can therefore win by arrival path. The 2.5-second rule is a heuristic, not cross-source freshness proof.

### Options and recommended boundary

1. **Make native snapshots the playback authority; keep App as a narrow overlay producer.** Native `media-update` and the initial full command snapshot remain sole owners of play state, position, duration and capabilities. App sends only track-keyed artwork/metadata enrichment and seek intent/rollback overlays, each tied to source/title/artist identity and an App-local operation id. This removes playback arbitration and avoids confusing wall-clock time with order. It is the smallest long-term ownership model, but requires changing the current sync payload and Floating merge logic; seek confirmation/rejection and enrichment after track switch need explicit tests.
2. **Keep both sources but sequence them.** The sixth slice adds only consumer instance tokens and an App reattach query; it does not add shared playback revisions. A complete dual-authority protocol would need monotonically increasing revisions scoped to each producer and the originating native snapshot revision on derived App data. That preserves current behavior but adds protocol state and still leaves two playback authorities. `Date.now()` cannot serve as a cross-source revision.

**Next authority slice recommendation:** retain the current ready-query/replay handshake. Evaluate native snapshots as sole playback owners with App-only track-keyed artwork/metadata and seek intent/rollback overlays, versus adding a backend-native revision to every raw snapshot and command result. Do not use `Date.now()` as a revision. No-consumer broadcast gating remains separate: this implementation intentionally does not gate on open state because no reliable closed lifecycle / acknowledgement protocol was added. The handshake closes the open-before-listener and stale-delta-baseline gaps; it does **not** prove event consumption or resolve later raw-vs-sync playback ordering.

The handshake acceptance cases are: a new same-track consumer receives full artwork despite an older sender acknowledgement; an unavailable initial snapshot still leads to ready; an App reload queries and receives the token from an already-ready Floating instance; duplicate ready tokens do not reset the baseline; a prior-generation in-flight success cannot acknowledge the new consumer; unmount during a deferred initial snapshot emits no late ready. The App readiness gate additionally verifies that a ready reply before App native media does not replay default/remembered state, the first native update replays current state, an actual empty-source event clears it, and a disposed App does not replay. It deliberately does not gate broadcasts when no Floating window is open, does not promise actual per-listener receipt, and does not establish cross-source ordering. A generation reset cannot retract an old payload already physically dispatched through Tauri, so stale in-flight arrival at a new consumer remains unresolved. This plan makes no native UI measurement claim.

## Fifth-slice implementation and verification: App sync sender

- Added `src/lib/mediaSyncSender.ts` as a small App-specific sender rather than generalizing the region geometry sender. It retains one in-flight dispatch and one replaceable pending **full local snapshot**. It decides whether to omit artwork only when dispatching, comparing against the last snapshot whose Tauri `emit` resolved successfully.
- On successful dispatch, only that dispatched snapshot advances the acknowledged track/art baseline; a newer pending snapshot remains intact and is sent next. On failure, the baseline is unchanged, the latest full snapshot stays pending, and the sender performs at most three exponential backoff retries (default 250/500/1000 ms). A later ordinary sync replaces the pending value and triggers a new attempt. Failures are caught and reported, not left as unhandled rejections. Disposal clears pending work and retry timers; in-flight completion after disposal is ignored.
- Preserved `island-media-sync` and its payload fields, including `artworkResolved`, projected playback position, optimistic seek and rollback snapshots, and empty-source state. No `isFloatingWindowOpen` gate or per-listener receipt acknowledgement was added; the next slice adds a readiness query/replay but still cannot prove a listener consumed an emit or order it against raw Rust events.
- Added deferred sender tests for replacement then same-art omission, explicit clear, failed emit followed by same-track sync, in-flight B replaced by C, bounded retries and disposal. Added an actual App lifecycle fixture case: reject the first `island-media-sync` emit, then deliver a same-track native payload with artwork omitted; the next App dispatch retains the artwork. Sender tests pass 6/6; App emit-failure fixture plus existing Floating/Studio snapshot/init cases pass 7/7; `svelte-check` reports 0 errors and 0 warnings; `pnpm run build` succeeds (3,870 modules).

## Sixth-slice implementation and verification: ready token replay

- Added `FLOATING_MEDIA_READY` and `FLOATING_MEDIA_READY_QUERY` event names. A Floating instance creates one `crypto.randomUUID()` token, installs both media listeners and its ready-query listener, then handles the initial full native snapshot. Whether the snapshot succeeds or fails, it announces that token afterward. A later ready query re-announces the same token. The disposed guard prevents a late snapshot completion from announcing ready after unmount.
- After the App registers its ready listener and raw media listener, it emits one ready query. On a new ready token, `mediaSyncSender.resetForConsumer(token)` invalidates its artwork acknowledgement baseline and drops any stale pending snapshot; App then offers the current full state. A repeated token is idempotent. Sender candidates carry a local generation: if an old consumer's in-flight emit resolves after a new token, it cannot update the new generation's baseline; the latest new-generation full snapshot is sent once the single in-flight dispatch settles.
- The query/replay path deliberately does not gate broadcasts when no Floating consumer exists and adds no native window lifecycle or closed-state changes. It closes listener-install timing and stale acknowledged-cover issues for a newly ready consumer, but Tauri emit resolution still does not prove actual per-listener consumption and the raw/sync playback sources still have no shared revision.
- Added deferred sender coverage for same-track full cover on a new token, duplicate-token idempotency, and prior-generation in-flight success. Added two-end lifecycle coverage for listener-after-App ordering with initial snapshot failure, App reload query against an already-ready Floating instance, and unmount during a deferred first snapshot with no late ready event. Plus existing failed-emit/Floating/Studio regressions: sender tests pass 8/8; the targeted App/Floating/Studio Playwright set passes 10/10; `svelte-check` reports 0 errors and 0 warnings; `pnpm run build` succeeds (3,870 modules).

## Seventh-slice implementation: App native-media readiness gate

- Source trace found no App startup `getMediaInfo()` snapshot. `getMediaInfo()` is used only by the explicit resume-last-track flow and does not initialize App playback state. Remembered/local and demo/default state therefore cannot authorize a ready replay.
- App now keeps an instance-local `appNativeMediaReady` flag, initially false on every mount. Only an actual `media-update` event sets it, including a real empty-source event. A ready token always resets the sender's consumer/artwork baseline, but replay waits for readiness. Other sync triggers (open, seek, and cover enrichment) share the same guard. No native query, window-open heuristic, or timestamp comparison was added.
- Extended the App reload fixture: answer the ready query with no new App native data and verify no replay while Floating retains its song; the first native update emits the current full state and cover; true empty source sends an explicit clearing snapshot; after App unmount a late native event causes no App sync dispatch.
- Remaining boundary: sender generation prevents an old in-flight completion from acknowledging a new consumer, but an old payload already dispatched through Tauri can still physically arrive after reset and affect that consumer. A shared source revision/receipt protocol is still needed to eliminate that cross-source race.
- Verification: media-sync sender tests 8/8; App/Floating/Studio lifecycle Playwright suite 24/24; `pnpm run check` reports 0 Svelte errors and warnings; `pnpm run build` succeeds (3,870 modules).

## Next design: shared native revision and authority boundary (read-only proposal)

### Source evidence and ordering hazard

- `src-tauri/src/lib.rs::spawn_media_listener` owns a GSMTC manager, subscriptions, metadata cache, and the polling loop. Callbacks enqueue a capacity-one `Refresh` marker; the actor reads a snapshot and emits `media-update`. This is already the natural serialized observation owner. The emitted payload currently carries only `MediaState`; its `lastUpdatedTimestamp` is a wall-clock field, not a cross-source order token.
- `src-tauri/src/commands/media.rs::get_media_info_cmd` independently runs `services::media::get_media_info` on the general native-task pool. `FloatingWindow.svelte` registers its two media listeners, invokes that command for its initial snapshot, then arbitrates only against local event/artwork counters. It cannot compare a delayed result to another WebView's or actor's event.
- `control_media(play_pause)` runs independently, waits 150 ms, then directly emits an unversioned `MediaState` through `EVENT_BUS.emit`; actor refresh can publish the same change separately. `seek_media` is also an independent native command. Stamping results when a query completes would let a slow old query acquire a numerically newer value than a newer actor event.
- App currently maps raw native payloads to local playback state and sends a top-level `island-media-sync` snapshot. The sender's generation only controls its artwork acknowledgement baseline. Floating's 2.5-second raw suppression rule uses arrival time (`lastIslandMediaSyncAt`), so it cannot tell which source state is newer. Existing per-WebView snapshot tokens do protect one Floating initial query from some locally observed event races, but they are not shared across App/Floating.

### Preferred protocol shape

- Add a process epoch UUID and monotonically increasing `nativeRevision` assigned by the media actor before it publishes an observation. Keep `lastUpdatedTimestamp` solely for playback position projection. Epoch mismatch starts a new sequence domain; since windows belong to the same Tauri process, process restart also restarts consumers. Revisions are never compared across epochs.
- Make the actor the authority for native playback snapshots and state-changing controls. Actor messages should carry replies for `get_media_info_cmd` and control requests. A query either returns the actor's cached full snapshot at its existing revision or asks that same actor to refresh and allocate a revision before responding; it must not independently sample on another worker and allocate a revision after completion. `control_media` should execute/confirm through the actor and publish once, removing its direct unversioned confirmation emit. The existing capacity-one refresh marker may remain coalescible, but request/reply operations must not be dropped behind it.
- Preserve top-level `MediaState` payload fields for compatibility and add the native stamp additively. `media-update` and App relay must carry the exact same `{epoch, revision}` for the same playback snapshot; App must not mint a playback revision. `albumArt` omission remains a same-track delta (preserve current art); `albumArt: ""` remains an explicit clear. Full snapshot command/ready replay always includes album art, including empty string. Confirmed empty session is a normal newer full native revision with `source: ""` and explicit empty art.
- Split App-only data from native playback authority. App relay may include a separate overlay section keyed by the native epoch/revision and track identity: HD artwork/metadata enrichment plus optimistic seek position/rollback state. These enrichments can apply only to their matching native basis and must not overwrite playback fields from a newer native revision. Track changes, true empty source, newer native revision, or failed/stale command results invalidate the relevant seek overlay according to explicit rules.
- Give each App mount a random session token and overlay counter, but do not treat random tokens or local counters as cross-session ordering. On a new App session, Floating replaces its accepted App session token after receiving the session-start event; it ignores overlays from prior sessions thereafter. New App replay waits for the existing readiness handshake and includes its current native basis. Tauri emission is still only dispatch acceptance, not proof that every listener consumed the message.
- Floating stores the latest `(epoch, nativeRevision)` and rejects a lower revision in the same epoch for playback; equal revision is idempotent for playback but can carry a matching App overlay. On a new epoch it resets native order and accepts the first stamped snapshot. A legacy unstamped payload can be accepted only before that consumer enters stamped mode; after that, legacy traffic cannot roll playback back. Keep current event names, with additive fields during migration.

### Option comparison and recommendation

| Option | What it fixes | Cost / failure mode | Assessment |
| --- | --- | --- | --- |
| Actor-owned cached snapshot and request/reply commands | One authority assigns observation order; delayed get snapshot cannot be relabeled newer; actor and `control_media` stop publishing duplicate unversioned playback | Add request/reply messages and runtime handle; keep them non-droppable while refresh markers coalesce; route control and snapshot through the COM-owning worker; requires short Rust actor lifecycle and serialization tests | **Preferred safe design.** Uses the existing actor/cache and eliminates the ambiguity at its source. |
| Keep independent native commands and arbitrate locally | A shared atomic ticket reserved before each native read can reject late completions with older request tickets | Ticket order describes request start, not actual sample time; slow reads may be rejected even when they sample newer state, and assigning on completion recreates the stale-query bug. Every control/direct emission must also reserve/order a ticket. Not a single source of truth | Smaller temporary guard only; not sufficient as final I3 authority contract. |

### Smallest implementation slices

1. **Backend authority and stamp (first implementation slice):** introduce the stamp/envelope types and actor-owned revision counter; add non-droppable actor request/reply for full snapshot; route `get_media_info_cmd` and `control_media` confirmation through that actor; keep raw payload fields and event name, add stamp; preserve full/delta artwork semantics. Add deterministic Rust tests for query-before/after-refresh ordering, coalesced refresh vs retained requests, control confirmation emitted once, epoch reset, omitted vs explicit-clear art, and full query snapshot. No frontend ordering behavior changes yet; old clients ignore additive fields.
2. **Floating native revision gate:** type the additive stamp; replace the 2.5-second wall-clock playback suppression with epoch/revision comparison; initial snapshot uses returned stamp and is discarded if an equal/newer event arrived; duplicates are idempotent; art-only same-basis enrichments remain possible. Add deferred command/query race tests and raw event replay tests.
3. **App overlay and reload session:** relay the native stamp unchanged and split playback from App-only artwork/seek overlay; add mount session token + overlay sequence acceptance; ensure an old App session cannot change a new session's overlay. Exercise App reload with an old in-flight event, HD cover completion, optimistic seek/rollback, track switch, empty state, and new Floating full snapshot. Keep the current App readiness gate.

This proposal does not promise event receipt acknowledgement. The backend revision orders native observations; the App session token fences stale enrichment after a newer session has registered. It does not retract an already-dispatched event that arrives before the new session-start event is processed, and it must not claim stronger end-to-end delivery guarantees than Tauri provides. I3 remains unchecked; this audit made no production-code changes and ran no tests.

## Ninth-slice implementation: frontend native revision gate

- App validates each raw native stamp before mutating media state. Lower revisions in the active epoch, malformed/missing stamps after stamped mode begins, and events from retired epochs are ignored. A native event may establish a new opaque epoch; the previous epoch is retired. App's floating snapshot carries the accepted `{nativeEpoch, nativeRevision}` unchanged, including App-only artwork enrichment and local seek projection; no local wall-clock value is used as a media revision.
- Floating now compares raw events, command snapshots, and App relay snapshots against one native basis. Same-epoch lower revisions are dropped before snapshot/artwork fallback, including empty-session clears. Higher revisions advance playback. Same-revision raw and command playback are idempotent; same-revision command snapshots may fill only missing artwork, and same-revision App relays may enrich artwork and the existing position/timestamp projection without replaying track identity, play state, duration, or capabilities. A newer explicit empty session clears; omitted artwork continues to preserve same-track art.

Raw native events and initial command snapshots can establish a new epoch; an App relay can bootstrap an uninitialized Floating consumer but cannot switch an existing consumer to another epoch. Retired epochs are rejected. Legacy unstamped messages remain accepted before stamped mode only. Existing local initial-snapshot track/artwork tokens remain in place; stamp rejection runs first so a stale command cannot resurrect a cover through the artwork-only path.

## Tenth-slice implementation: App overlay sequence and session fence

- Each App mount creates an opaque UUID session and a safe-integer overlay counter. Every full sync offer increments the counter and carries `appSessionId`, `overlaySeq`, and an `appOverlay` bound to the exact native epoch/revision and source/title/artist track key. The serialized sender retains the latest full snapshot, so coalescing may skip sequence values but cannot dispatch them backwards. Counter exhaustion stops relay offers for that mount rather than wrapping or emitting an inexact number.
- Reused the existing `floating-media-ready-query` as an explicit App-session declaration. App sends its session after registering its READY listener; a newly mounted Floating can request a declaration by announcing ready without a session. Floating adopts only sessions declared through this handshake, retires the previous session, and includes the active session in its READY acknowledgement. App replays only after it receives an acknowledgement for its own session and resets the sender baseline per `{session, floating instance}`. This covers either mount order and App reload without a generic message bus.
- Floating rejects session-tagged relays from unknown or retired sessions and, after session mode starts, rejects relays without a session. Same-native-basis enrichment requires the active session, a strictly higher safe overlay sequence, matching native basis, and matching track identity. Sequence gaps from sender coalescing are valid. Newer native basis advances only through the native revision gate and makes old-basis overlays ineligible. A same-revision raw duplicate skips artwork reconciliation while App overlay art for that basis has been accepted, so it cannot downgrade HD art or undo an explicit clear. Same-revision initial command snapshots remain missing-art-only; explicit clears are never used to repopulate artwork.
- App overlay artwork/metadata/position are applied through the separate overlay object. Playback state, play/pause, duration, capabilities, and track changes continue to come from the native basis. Seek optimistic updates and rollback both create newer offers in the same App session; latest-snapshot coalescing can skip the optimistic sequence if a later rollback is already pending, but cannot deliver rollback before optimistic state. The READY handshake and unmount cleanup remain bounded by the existing listener/sender lifecycle.
- The fence cannot retract an old relay already dispatched before Floating processes the new session declaration. Such a relay may still apply during that interval. Tauri emit acceptance is not proof of listener consumption; session ordering begins when Floating receives the explicit query declaration. This boundary is recorded and I3 remains unchecked.
- Added tests for active/retired session acceptance, sequence gaps/duplicate rejection, new-session first overlay, old-session relay rejection after App reload, newer native basis over old overlays, same-revision raw art preserving HD cover, initial command snapshot artwork semantics, seek rollback sequence, listener readiness, and dispose behavior.

## Thirteenth-slice implementation: timer deadline/state fanout

- Added the shared `TimerSnapshot` type with status, duration, absolute `endsAt`, exact paused `remainingMs`, label, App session ID, state revision, first-session marker, and optional request ID. App emits only when the countdown state signature changes (start/pause/resume/adjust/reset/completion/label/deadline), not when `clockNow` updates. Running snapshots calculate `remainingMs` against `Date.now()` at dispatch and include the authoritative deadline; the existing App deadline/completion behavior is unchanged.
- Timer state emit failures are caught and logged. The acknowledged revision advances only after Tauri accepts an emit; there is no automatic retry loop. An on-demand TimerWindow request always forces a fresh snapshot, so a missed event can be repaired at mount/resume without background retry churn.
- App session ID plus monotonically increasing state revision fences delayed events. The first successfully accepted snapshot in a new App session carries `sessionStart`; an already-running TimerWindow can switch to that session and retire the previous one. TimerWindow accepts a session transition only from its matching request response or explicit first-session marker, rejects lower/duplicate revisions and retired sessions, and requests state after registering its listener at initial mount and when becoming visible.
- TimerWindow computes running time from `endsAt - Date.now()` and schedules only the next displayed-second boundary while visible. Hidden mode cancels its local tick; visible mode recalibrates immediately and requests a current snapshot. Paused state keeps its exact remaining milliseconds. Older unversioned snapshots without `endsAt` retain the prior received-time interpolation fallback; once a versioned session is active, unversioned events cannot roll it back.
- TIMER_ACTION event names/payloads and App countdown transition helpers were not changed. No Rust code or generic sender platform was introduced.
- Added lifecycle coverage for: no per-second state broadcasts during a 6-second running interval; start/pause/resume/adjust deadlines and revisions; a state delivered after 6 seconds still displays the 4 seconds remaining to `endsAt`; hidden timer window has no local display-second tick; visible resume and remount request the current snapshot; retired session events cannot overwrite a new App session; hidden deadline completion is emitted once; and unmount clears the TimerWindow-owned short timeout.
