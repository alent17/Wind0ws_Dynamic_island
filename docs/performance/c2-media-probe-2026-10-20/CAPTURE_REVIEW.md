# C2 Capture monitor review

## Scope and source paths

Static review of `src-tauri/src/lib.rs` (`CaptureMonitorPreferences`, `capture_monitor_preferences`, `start_capture_monitor`, `detect_fullscreen_app`), `src-tauri/src/commands/settings.rs` (`commit_settings_transaction` and `apply_external_changes`), the capture-mode consumers in `src/App.svelte` and `src/FloatingWindow.svelte`, `src/lib/captureMode.ts`, its existing tests, and the locked `windows 0.52.0` bindings. No product process, capture tool, global input, or user setting was exercised.

## Implemented behavior and path review

- Preferences are re-read when `AppState.settings_revision` changes. A poisoned preferences mutex falls back to all three implemented native detectors enabled, preserving the privacy behavior rather than silently disabling detection.
- Screenshot detection is gated by `capture_hide_on_screenshot`: only when enabled does the loop call `GetAsyncKeyState` for Print Screen and Win+Shift+S. The loop cadence is 50 ms while enabled, and a detected press is held for 1.5 seconds. This path does not depend on fullscreen or recording preferences.
- Fullscreen detection is gated independently by `capture_hide_on_fullscreen`: `detect_fullscreen_app` is called every 500 ms only while enabled. It checks the foreground window against its nearest monitor for borderless full coverage. The independent `check_fullscreen_app` command remains a separate on-demand path; disabling the background preference does not remove or disable that command.
- Recording detection is gated independently by `capture_hide_on_recording`: only this preference enables `AppCapture::GetForCurrentView` and `IsCapturingVideo` polling. `GetForCurrentView` construction failures already schedule a 30-second retry. This review found that `IsCapturingVideo` errors on an existing object previously fell through to `false` but retained the object, so every next 500 ms poll called the failing API again. That error path now drops the stale interface and shares the 30-second retry interval. The existing fail-open state behavior remains: on a query error `is_recording` becomes false, so a transient failure while capture is active may restore visibility during that retry window. Changing that privacy-versus-stuck-hidden policy needs a separate product decision. Turning recording detection off drops the cached interface on the actor thread; a later false-to-true preference transition resets the retry deadline and capture poll to now.
- Cadence is 50 ms if screenshot is enabled, otherwise 500 ms if recording or fullscreen is enabled, otherwise 1000 ms. With all three native detector preferences disabled, the worker still wakes every second, reads the settings revision, and emits a state only if it differs from its last snapshot; the gated calls to `GetAsyncKeyState`, `detect_fullscreen_app`, `GetForCurrentView`, and `IsCapturingVideo` are skipped. `Apartment::enter` still performs COM initialization once when the worker starts; that is apartment setup, not a capture detector call.
- When a detector is disabled, its state is cleared in the worker loop. If the aggregate capture snapshot changes, `capture-mode-changed` is emitted. `App.svelte` recalculates capture reasons and calls `showWindow()` when no enabled reason/manual hide remains; `FloatingWindow.svelte` derives visibility from the same snapshot and current settings. Settings revision is polled rather than signaled directly, so an off-state restore may wait for the prior loop sleep (at most 1 second while all disabled, 500 ms in the other non-screenshot modes, or 50 ms while screenshot mode is enabled). Re-enabling is observed at the next loop, then that detector is queried on its next due check; recording explicitly resets its retry deadline. An independent manual ten-second hide remains active by design and is not cleared by capture-state changes.
- `capture_hide_on_screen_share` is persisted and participates in settings-change detection, but `screenShare` is always emitted as `false`; the UI labels sharing detection unavailable. Do not count it as implemented.
- The capture worker is a detached thread with no explicit stop/join or lock/power notifications. It registers no WinRT events, owns its apartment and capture interface on that worker, and naturally stops with process termination. After lock/suspend it relies on the next poll; a failed stale AppCapture read now drops the interface and retries after 30 seconds. This behavior was reviewed statically, not exercised across lock/unlock, suspend/resume, or graceful process shutdown.

## API boundary

The locked Rust binding exposes `AppCapture::GetForCurrentView() -> Result<AppCapture>` and `IsCapturingVideo() -> Result<bool>`. Microsoft's [AppCapture documentation](https://learn.microsoft.com/en-us/uwp/api/windows.media.capture.appcapture?view=winrt-28000) describes `GetForCurrentView` as returning the instance for the current view and `IsCapturingVideo` as reporting whether another app is currently capturing video. This is not a general system-wide recorder detector and should not be described as covering every third-party recorder. The worker calls a current-view API from its own MTA thread, while Tauri's UI view lives elsewhere; whether this succeeds in the real product host remains an explicit native-runtime question. The settings hint already narrows the feature to Windows-reported AppCapture status.

## Offline verification and remaining evidence

After the retry change, `cargo check --offline --lib` passed with the existing isolated target. Existing focused unit tests passed 3/3 (`capture_monitor_tests`): the 50 ms screenshot cadence, 500 ms recording/fullscreen cadence, and 1 second all-off cadence. They cover interval policy, not live WinRT call counts or the 30-second runtime retry. `git diff --check` passed.

Still requiring an approved native/product regression: exact detector-call counts while toggling each preference, AppCapture success/failure and actual Windows recorder coverage, UI hide/restore while toggling during active capture, and lock/unlock or suspend/resume. The fail-open behavior after an AppCapture query error is an additional privacy limitation to review. During that review batch no Release was rebuilt, no global input or user setting was changed; C2 remains open.
